# 布谷(Bugu)需求文档

> 名字取自布谷鸟:到点报时。命令行为 `bugu`。版本:草稿 v0.6,2026-11-11。

## 1. 一句话定位

一个给个人用的、桌面优先的定时任务应用:不用写配置文件,点几下或者对 AI 说一句话,就能让 Claude Code、Codex、Pi 等命令行 agent 或普通脚本按时干活,结果送到你面前。

- **桌面应用是入口,也是主战场。** 菜单栏驻留、表单建任务、收件箱、系统通知是产品的核心体验,不是附属界面。
- 同一个程序也能无界面部署到服务器,在桌面应用里统一查看。
- 软件本身不内置任何 AI 能力,不调用任何模型接口,不持有任何密钥。

## 2. 背景

### 2.1 问题

用户已经在用 Claude Code、Codex、Pi 等命令行 agent,并希望它们定时自动干活。现有方案各有缺口:

| 方案 | 缺口 |
|---|---|
| cron、launchd | 环境变量不全导致 agent 跑不起来;只看退出码;没有运行记录;睡眠时错过的任务直接丢失 |
| 各厂商自带的定时功能 | 只调度自家 agent;本地版要求应用常开,云端版碰不到本地文件 |
| Dagu 等工作流引擎 | 能力最全,但必须写 YAML,面向服务器和运维,没有桌面应用,许可证为 GPL-3.0 |
| 第三方 agent 调度器(Open Run、herdr-automations、cronagent 等) | 全部围绕代码仓库设计(工作树、分支、PR);面向开发者;结果处理薄;AI 不能反过来管理任务 |

### 2.2 机会

引擎层的能力已经不是空白。Dagu(2022 年至今,GPL-3.0)已经具备:16 种 AI 命令行适配和自定义适配、跨运行的持久状态、补跑窗口、通知、webhook 触发、供 AI 读取和修改任务的 MCP 服务。Bugu 不在引擎能力的数量上与它竞争。

Bugu 的空间在体验层:

1. **不用写配置。** Dagu 的任务必须写 YAML,网页界面里也是 YAML 编辑器,且是带步骤依赖的工作流模型。Bugu 用表单建任务,模型只有"一个触发、一串顺序步骤、若干通知",界面上是一排卡片而不是画布。
2. **桌面优先。** 现有工具都没有桌面应用:没有菜单栏驻留、系统通知、点通知直达结果、睡眠唤醒后的处理。
3. **结果是给人看的。** 收件箱、Markdown 渲染、没有新内容就不打扰,围绕"每天看一眼"设计。
4. **个人电脑是一等公民。** 沿用终端里的登录态,开机自启,不需要像服务器那样运维。
5. **许可证宽松。** 便于被嵌入和二次分发。

### 2.3 不做什么

- 不做"定时让 agent 改代码并开 PR"的完整工作流(Open Run 已做得很完整)。
- 不做云端托管执行(用户可以自行部署到自己的服务器)。
- 不做多机集群、任务分发、主备切换。每个实例各自独立。
- 不做流程编排(多步骤依赖、分支、并行)。
- 不内置模型调用、提示词优化等 AI 功能。
- **范围红线:一个任务只有一个触发配置、一串按顺序执行的步骤、若干通知配置。** 不做分支、循环、并行、子流程和画布连线。需要这类逻辑时,由 AI 步骤在提示词里自行处理,或使用 Dagu 这样的工作流引擎。

## 3. 目标用户

| 用户 | 特征 | 第一版是否覆盖 |
|---|---|---|
| A. 重度使用 agent 命令行的开发者 | 会写配置文件,习惯终端 | 是,主要用户 |
| B. 技术团队里的非技术同事(运营等) | 不写代码,由同事帮忙配好运行器 | 是:通过桌面应用的表单建任务,运行器由同事配好 |
| C. 完全独立的非技术个人用户 | 不会装命令行工具 | 否:仍需要有人帮忙装好 agent 命令行 |

## 4. 核心概念

| 概念 | 含义 |
|---|---|
| 任务(task) | 一条"什么时候、用什么、做什么"的定义 |
| 步骤(step) | 任务中按顺序执行的一环。类型有三种:AI 命令行、脚本、文本 |
| 运行器(runner) | 对一个命令行工具的声明式描述:怎么启动、提示词怎么传、输出什么格式、怎么算成功 |
| 运行(run) | 任务的一次执行,有唯一编号、状态、输出、产物 |
| 状态目录(state dir) | 每个任务专属的持久目录,供任务跨次运行保存数据(如已读列表) |
| 收件箱(inbox) | 所有运行结果的汇总视图,区分已读和未读 |
| 后台(daemon) | 负责调度和执行的常驻部分。可以由桌面应用承载,也可以单独以 `bugu serve` 运行 |
| 主机(host) | 一个正在运行的后台实例,用地址加令牌标识。可以是本机,也可以是服务器 |
| 令牌(token) | 访问后台接口的凭证 |

一个任务由三部分组成:

```
触发 → 步骤 1 → 步骤 2 → … → 结果去哪
```

每个步骤是以下三种之一:

- **AI 命令行**:选一个运行器,写一段提示词,由 Claude Code、Codex、Pi 等自己完成。
- **脚本**:填一个脚本文件的路径,或一条命令。传统定时任务就是只有一个脚本步骤的任务。
- **文本**:一段固定文本,原样作为这一步的输出。用来给后面的步骤提供固定背景或要求,或作为通知正文的模板。

只有一个步骤的任务是最常见的情况,界面上不强调"步骤"这个概念,需要时再添加。

## 5. 架构

### 5.1 总体原则

**一个程序,多种界面,共用一个后台。** 参考 yetone/magpie 的做法:`bugu` 是单个可执行文件,用子命令决定以什么形态运行。所有界面都通过后台的 HTTP JSON 接口工作,不直接读写任务文件和数据库。

```
                    bugu(单个可执行文件)
┌──────────────────────────────────────────────────┐
│  菜单栏   主窗口   浏览器        命令行   AI agent │
│     └───────┴────────┘             │         │    │
│       同一份内嵌的网页前端           │         │    │
│               │                    │         │    │
│          HTTP JSON 接口(令牌认证) ──┴─────────┘    │
│               │                                   │
│        后台:调度、运行器、执行、存档、通知          │
└──────────────────────────────────────────────────┘
```

| 子命令 | 形态 |
|---|---|
| `bugu` 或 `bugu app` | 桌面应用:菜单栏图标加主窗口,同时提供后台 |
| `bugu serve` | 只运行后台,无界面,用于服务器 |
| `bugu web` | 后台加网页面板,用于没有桌面的机器 |
| `bugu <其他命令>` | 命令行客户端,连接正在运行的后台 |

### 5.2 部署形态

| 形态 | 部署 | 管理方式 |
|---|---|---|
| 个人电脑 | 安装桌面应用,设置为开机自启并驻留菜单栏 | 应用窗口、本机命令行、AI agent |
| 服务器 | 安装无界面构建的 `bugu`,用 `bugu daemon install` 注册为 systemd 服务 | 浏览器打开其网页面板,或在桌面应用里打开它,或命令行加 `--host` |

各实例相互独立,互不感知。不做集群和任务分发。

### 5.3 后台只运行一份

- 任何形态启动时,先检查本机是否已有 `bugu` 在提供服务。有则只作为它的界面,没有才自己启动后台。
- 桌面应用关闭窗口只是隐藏,程序留在菜单栏,任务照常运行。
- 用户主动退出应用且存在已启用的任务时,先提示"退出后任务将不再运行"。
- 想让任务不依赖应用是否开着的用户,可以在个人电脑上同样执行 `bugu daemon install`,把后台装成系统服务,应用检测到后只做界面。

这一条修改了 v0.3 的决定。v0.3 要求应用与后台必须是两个进程;现在改为默认由应用自身承担后台,靠开机自启、菜单栏驻留和退出提示来保证任务不被意外停掉。好处是安装即用,不需要应用去注册和维护另一个系统服务。

### 5.4 连接方式

统一为 HTTP 加令牌,不使用 Unix 套接字,也不内置 SSH 通道。

- 后台监听一个 HTTP 端口,同一端口同时提供接口和网页面板。
- 本机命令行自动读取本机令牌文件;通过 `--host` 连接其他主机。
- **远程管理即打开对方的网页。** 桌面应用里添加"另一个 Bugu"时填写地址和令牌,应用在自己的窗口里加载那台主机的网页面板。本机不代理任何请求,也不需要第二套传输方式。

安全要求见 7.10。

### 5.5 界面

- 前端只写一套,内嵌在可执行文件中,由后台的 HTTP 处理器提供。
- **前端只通过 JSON 接口与后台通信,不使用桌面框架的绑定机制。** 这样应用窗口、浏览器、远程主机三种情况走的是完全相同的路径。
- 桌面框架使用 MyGo(egoist/mygo),只负责开窗口、菜单栏图标、系统通知、开机自启、打包与自动更新。框架版本号为 0.9,尚未到 1.0;由于业务逻辑和前端都不依赖它的绑定,更换框架的损失很小。
- 设置等写操作的逻辑放在界面包之外,命令行和界面调用同一个函数。

已核实的 MyGo 能力(依据其仓库文档,2026-11-11):

| 需要的能力 | 是否提供 | 说明 |
|---|---|---|
| 菜单栏图标 | 是 | `NewTray`,可带菜单;可隐藏 Dock 图标 |
| 关闭窗口后驻留 | 是 | 监听 `OnWindowAllClosed` 即不退出 |
| 系统通知 | 是 | 支持点击回调;macOS 上只有打包后的应用能显示,首次会询问授权 |
| 开机自启 | 是 | `SetOpenAtLogin`,可判断是否由开机启动以便静默启动 |
| 签名与公证 | 是 | `mygo build` 生成应用包和磁盘映像;分发给他人需要 Developer ID |
| 自动更新 | 是 | 内置,从 GitHub 发布或任意 HTTPS 服务器获取签名的更新 |
| 界面自动化测试 | 是 | 自带 automation 插件,可读取界面元素、模拟输入、截图 |
| 纯 Go 的 SQLite | 是 | 官方插件,无 cgo |
| 许可证 | MIT | 可用于开源或闭源产品 |

### 5.6 代码组织

- 一个 Go 模块,一个产物。`main.go` 只做启动,全部逻辑在 `internal/` 下。
- `internal/` 按职责平铺小包,例如 `schedule`、`runner`、`exec`、`store`、`notify`、`api`、`client`、`cli`、`gui`,不设笼统的 core 包。
- 界面相关代码通过构建标签隔离:无界面构建不包含 MyGo,用于服务器和容器。
- 全程不使用 cgo。

### 5.7 两种环境的差异

| 差异点 | 个人电脑 | 服务器 |
|---|---|---|
| 开机自启 | launchd | systemd |
| 通知 | 系统通知为主 | 无桌面,只用 webhook 和机器人 |
| 睡眠补跑 | 必需 | 重启后同样适用 |
| agent 登录态 | 沿用终端里的登录 | 需在服务器上单独登录或配置密钥,`bugu doctor` 负责检查并提示 |

## 6. 典型场景

### 场景一:定时看 GitHub issue

开发者希望每个工作日 9 点收到一份新 issue 的分类报告。

- 需要知道"上次运行之后"的时间点。
- 只允许 AI 读,不允许回复或修改。
- 结果是一份 Markdown 报告,通过系统通知提醒,点开可读。

### 场景二:定时看几个网站的新闻

每天三次查看指定网站,只推送新内容。

- 需要跨次运行记住已看过的条目。
- 没有新内容时不通知。
- 电脑睡了一天,醒来只补跑一次。

### 场景三:运营定时取数据并存档

运营每天 18 点要一份数据日报,存到指定文件夹。

- 使用技术同事包装好的自定义命令行。
- 产物是带日期的文件,文件确实生成才算成功。
- 完成后推送到飞书。

### 场景四:传统定时任务

每晚 2 点执行备份脚本,失败时通知。与上面三类任务在同一处管理、同一处看记录。

### 场景五:让 AI 自己建任务

用户在 Claude Code 里说"以后每天早上帮我看一下这个仓库的 issue",agent 调用 `bugu add` 完成创建,并把结果告诉用户。

## 7. 功能需求

优先级:P0 为第一版必须有,P1 为第一版之后尽快补,P2 为远期。

### 7.1 调度

| 编号 | 需求 | 优先级 |
|---|---|---|
| S1 | 支持标准 cron 表达式 | P0 |
| S2 | 支持一次性任务(指定某个时间点执行一次) | P0 |
| S3 | 调度基于墙上时钟计算,不依赖长定时器,保证睡眠唤醒后行为正确 | P0 |
| S4 | 错过补跑策略,按任务配置:不补、只补最近一次(默认)、宽限时间窗 | P0 |
| S5 | 同一任务上一次还在运行时,新的触发跳过并记录,不排队 | P0 |
| S6 | 互斥组:同组任务不同时运行(用于同一工作目录的多个 agent 任务) | P1 |
| S7 | 重启后不重复触发已处理过的时间点 | P0 |
| S8 | 手动立即运行、暂停、恢复任务 | P0 |
| S9 | 更友好的时间写法(如"工作日 09:00") | P1 |
| S10 | 非时间触发:文件变化、webhook | P2 |
| S11 | 从 crontab 导入:解析并预览,导入的任务默认禁用,不修改也不删除原有条目 | P1 |

### 7.2 运行器

| 编号 | 需求 | 优先级 |
|---|---|---|
| R1 | 运行器用声明式配置描述,核心不写死任何厂商逻辑 | P0 |
| R2 | 自带 Claude Code、Codex、Pi 三份预设 | P0 |
| R3 | 用户可自定义运行器,与预设地位相同 | P0 |
| R4 | 提示词三种传递方式:命令行参数、标准输入、临时文件 | P0 |
| R5 | 输出格式声明:纯文本,或 JSON 加字段路径(提取最终结果、花费、会话编号) | P1 |
| R6 | 成功判定可配置:退出码(默认)、输出包含或不含某字符串、产物文件存在 | P0 |
| R7 | 运行器可声明"只读模式"和"无人值守模式"各自对应的参数,任务按需选择 | P1 |
| R8 | `bugu runner check` 检查运行器是否已安装、能否启动 | P0 |

三档接入深度:

- 第 0 档:任意命令,只看退出码和输出文本。
- 第 1 档:声明了提示词传递方式,可以用于 AI 命令行步骤。
- 第 2 档:声明了结构化输出,可以统计花费、续接会话。

### 7.3 执行环境

| 编号 | 需求 | 优先级 |
|---|---|---|
| E1 | 通过用户的登录 shell 启动子进程,保证 PATH、登录态与终端里一致 | P0 |
| E2 | 每个任务可指定工作目录和额外环境变量 | P0 |
| E3 | 总时长上限,超时后杀掉整棵进程树 | P0 |
| E4 | 无输出超时:多久没有新输出判定为卡死 | P1 |
| E5 | 启动时关闭标准输入,防止子进程等待人工输入 | P0 |
| E6 | 启动前预检:运行器是否存在、工作目录是否存在、输出目录是否可写;不通过则本次记为失败并说明原因 | P0 |
| E7 | 每个任务可指定时区,默认使用主机时区 | P0 |
| E8 | 支持环境变量文件,密钥通过它注入,不写进任务定义 | P0 |
| E9 | agent 要求人工确认而当前无法交互时,本次运行明确记为失败并说明原因,不静默绕过其权限机制 | P0 |
| E10 | 存档和通知中不出现明文凭证:环境变量文件里的值在输出中脱敏 | P0 |

### 7.4 模板变量

可在提示词、命令、输出文件名中使用:

| 变量 | 含义 | 优先级 |
|---|---|---|
| `{date}`、`{time}`、`{datetime}` | 本次运行的日期时间 | P0 |
| `{last_run}` | 上次成功运行的开始时间;首次运行时为任务创建时间 | P0 |
| `{state_dir}` | 本任务的状态目录路径 | P0 |
| `{run_dir}` | 本次运行的存档目录路径 | P0 |
| `{output_file}` | 本次应生成的产物文件完整路径 | P0 |
| `{task_name}` | 任务名 | P0 |
| `{prev}` | 上一个步骤的输出 | P0 |
| `{steps.<步骤名>.output}` | 指定步骤的输出 | P0 |

### 7.5 结果处理

| 编号 | 需求 | 优先级 |
|---|---|---|
| O1 | 每次运行落盘存档:元数据(状态、起止时间、实际执行的命令、退出码)和完整输出 | P0 |
| O2 | 输出过大时保留开头和结尾 | P0 |
| O3 | 运行状态:已排队、运行中、成功、失败、超时、跳过、错过、已取消、中断(后台或进程异常退出) | P0 |
| O4 | 静默条件:输出匹配指定标记时不通知,运行记为成功但标注"无内容" | P0 |
| O5 | 产物落盘:任务可声明输出目录和文件名模板 | P0 |
| O6 | 产物来源二选一:由 agent 自己写文件,或由调度器把最终输出保存为文件 | P0 |
| O7 | 存档保留策略:按天数或次数自动清理 | P1 |
| O8 | 失败自动重试,**默认关闭**(重试可能重复产生副作用),开启后可配置次数和间隔 | P1 |
| O9 | 每任务每日运行次数上限 | P1 |
| O10 | 花费统计与每日花费上限(依赖第 2 档运行器) | P2 |
| O11 | 每次运行保存当时的任务配置快照,之后修改任务不影响历史记录 | P0 |
| O12 | 结果信封:任务可在 `{run_dir}/result.json` 写入结构化结果(状态、摘要、产物列表、是否请求通知及通知内容)。有信封时以它为准,没有时退回到退出码和静默标记 | P0 |
| O13 | 只展示命令行实际提供的数据,拿不到的花费和用量不推测 | P0 |

### 7.6 通知

| 编号 | 需求 | 优先级 |
|---|---|---|
| N1 | macOS 系统通知,由桌面应用发出,点击可打开对应结果。无界面运行时没有系统通知,只走 webhook 和机器人 | P0 |
| N2 | 通知时机可配置:总是、仅失败、仅有内容时(默认) | P0 |
| N3 | 通用 webhook 通知 | P0 |

### 7.7 命令行

| 命令 | 作用 | 优先级 |

| `bugu add` | 新建任务(参数方式,或从文件读入) | P0 |
| `bugu list` | 列出任务及下次运行时间 | P0 |
| `bugu show <任务>` | 查看任务定义 | P0 |
| `bugu edit <任务>` | 修改任务 | P0 |
| `bugu rm <任务>` | 删除任务 | P0 |
| `bugu run <任务>` | 立即运行一次,`--dry-run` 只显示将执行的命令 | P0 |
| `bugu pause` / `bugu resume` | 暂停和恢复 | P0 |
| `bugu runs [任务]` | 运行历史 | P0 |
| `bugu logs <运行编号>` | 查看某次运行的输出 | P0 |
| `bugu inbox` | 未读结果列表 | P0 |
| `bugu runner list / add / check` | 管理运行器 | P0 |
| `bugu app` / `bugu serve` / `bugu web` | 以桌面应用、纯后台、后台加网页面板的形态启动,见 5.1 | P0 |

### 7.10 连接与安全

接口能创建任务,等同于能在主机上执行任意命令,因此认证从第一版就必须具备。

| 编号 | 需求 | 优先级 |
|---|---|---|
| C1 | 所有请求必须携带令牌,不提供免认证模式 | P0 |
| C2 | 首次启动自动生成令牌,保存在仅当前用户可读的文件中 | P0 |
| C3 | 默认只监听本机地址;对外提供服务必须显式修改配置 | P0 |
| C4 | 只认请求头中的令牌,不使用 Cookie,并校验请求来源,防止恶意网页请求本机端口 | P0 |
| C5 | 支持多个令牌,可单独作废 | P0 |

| C7 | 内置 HTTPS(配置证书路径) | P2 |

### 7.11 步骤

| 编号 | 需求 | 优先级 |
|---|---|---|
| T1 | 任务的数据模型为"触发、步骤列表、通知列表"。单步任务即只含一个步骤的列表,从第一版起就按此存储,避免日后迁移 | P0 |
| T2 | 步骤类型:AI 命令行(运行器加提示词) | P0 |
| T3 | 步骤类型:脚本。填写脚本文件路径或一条命令;解释器由文件自身或用户指定的命令决定 | P0 |
| T4 | 步骤类型:文本。一段固定文本,可含模板变量,原样作为该步输出 | P0 |
| T5 | 数据传递:上一步的输出自动作为下一步的输入;也可用 `{prev}` 和 `{steps.<步骤名>.output}` 引用;所有步骤共享同一个运行目录 | P0 |
| T6 | 某一步失败即停止,后续步骤不执行,运行记录标明停在哪一步 | P0 |
| T7 | 任一步骤可以声明"无事可做"(约定的退出码或结果信封),此时后续步骤不执行,本次运行不发业务通知。用于让便宜的脚本为昂贵的 AI 步骤把门 | P0 |
| T8 | 每个步骤有独立的超时和输出存档 | P0 |
| T9 | 界面:步骤显示为一排卡片,可添加、删除、拖动排序;运行时在卡片上显示每一步的状态和输出 | P0 |
| T10 | 单独试运行某一个步骤 | P1 |
| T11 | 在界面里直接编写脚本内容(由 Bugu 保存为文件) | P1 |
| T12 | 步骤类型:JS。内嵌纯 Go 的 JS 引擎,无需安装 Node,只开放读取输入、读写状态、发 HTTP 请求等有限能力 | P1 |
| T13 | 让 AI 代写步骤:用户描述需求,由 agent 通过命令行生成脚本和各步骤并建好任务 | P1 |

不做:分支、循环、并行、子流程。

## 8. 配置示例

任务定义存为文件,一个任务一个文件,可以放进版本管理。格式为草稿,以实现时为准。

```toml
# ~/.bugu/tasks/news.toml
name      = "news"
schedule  = "0 8,13,20 * * *"
runner    = "pi"
on_missed = "run_once"
silent_if = "NOTHING_NEW"
notify    = "system"
prompt    = """
查看以下网站的首页:……
对照 {state_dir}/seen.json 里已看过的标题,只挑新的,
每条写两句摘要并附链接,然后把新标题追加进 seen.json。
如果没有新内容,只输出 NOTHING_NEW。
"""
```

```toml
# ~/.bugu/runners/stats-agent.toml
name       = "stats-agent"
command    = "stats-agent run"
prompt_via = "stdin"
success_if = "exit_code"
```

```toml
# 传统定时任务:只有一个脚本步骤,可以用简写
name     = "backup"
schedule = "0 2 * * *"
command  = "~/bin/backup.sh"
notify   = "on_failure"
```

多步骤任务:先用脚本把门,有新内容才让 AI 运行。

```toml
name     = "issue-triage"
schedule = "0 9 * * 1-5"
notify   = "system"

[[steps]]
name   = "检查"
type   = "script"
path   = "~/bin/new-issues.sh"      # 没有新 issue 时以约定的退出码退出,后面不再执行

[[steps]]
name   = "要求"
type   = "text"
text   = "按 bug / 需求 / 提问 分类,标出今天必须处理的。只读,不要回复任何 issue。"

[[steps]]
name   = "分析"
type   = "agent"
runner = "claude"
cwd    = "~/workspace/my-project"
prompt = """
{steps.要求.output}

新 issue 列表:
{steps.检查.output}
"""
```

M1 没有包含、留给后续里程碑的:多个令牌与作废(C5)、`bugu token`、`bugu run --dry-run`、`--json` 输出、补跑策略的按任务配置(S4 目前固定为默认的只补最近一次)、时区(E7)、登录 shell 启动(E1)。任务文件和运行器配置目前是 JSON,第 8 章的 TOML 写法尚未支持。接口的客户端目前是手写的,13.3 的"从代码生成"尚未建立。

## 12. 待定问题

已确定:

- 产品名为布谷,英文和命令行用 Bugu / `bugu`。
- 实现语言为 Go,桌面应用使用 MyGo。
- 本机和服务器都可部署,连接方式统一为 HTTP 加令牌。
- 运营同事通过桌面应用或网页面板建任务。
- MyGo 的能力已核实,菜单栏、通知、驻留、签名、自动更新、界面自动化均支持;桌面框架维持 MyGo。
- 继续自研,以桌面应用为入口和主战场;不在引擎能力数量上与 Dagu 竞争。
- AI 命令行步骤默认只读,需要写权限时在任务里显式声明(决策记录 0008)。
- 采用单程序多形态的架构,界面只走 JSON 接口,远程管理即打开对方网页(参考 yetone/magpie)。

仍需确认,括号内是我的建议:

1. **开源还是闭源**(建议开源:这个品类很难靠软件本身收费,开源更利于被 agent 用户传播)。
2. **任务定义存文件还是数据库**(建议任务和运行器存文件,便于放进 git 后在服务器上拉取部署;运行记录存 SQLite)。
3. **服务器上的 Bugu 主要自己用,还是给团队多人用?** 后者需要把多用户和权限提前,目前按前者设计:令牌不区分权限。
4. **是否加入 Apple 开发者计划**:桌面应用要分发给其他人使用,需要 Developer ID 签名和公证,否则会被系统拦截。只自己用则不需要。(建议:等第一版可用后再办)
5. **是否支持 Windows**:Go 和 MyGo 都支持,成本在进程管理、PowerShell、后台驻留和测试。(建议第一版不做,代码里不写死平台)

## 13. 开发方式

本项目由 AI 编码 agent 承担绝大部分开发,人负责决策和验收。以下做法综合了子代理的审核意见和 yetone/magpie 的实践。

### 13.1 原则

1. 每个事实只写在一个地方。
2. 行为的准确定义以测试为准,测试名引用本文档的需求编号(如 S4、R6),不另写规格文档。
3. 规则尽量写成可执行的检查,而不是文字。
4. 权限靠分支保护和 CODEOWNERS 强制,不靠文档约定。
5. 文档只写现状;提案写在 issue 或合并请求里。

### 13.3 验证回路

| 对象 | 手段 |
|---|---|
| 调度、超时、补跑 | 可注入的时钟加假 agent(按脚本输出、延时、报错、卡死),不消耗额度,不依赖真实时间 |
| 架构约束 | `internal/archtest`:包依赖方向、核心包不出现厂商名、调度代码不直接读系统时间 |
| 接口 | 从代码生成客户端和文档,CI 检查重新生成后无差异 |
| 前端 | 浏览器测试,连接真实后台和假 agent |
| 桌面外壳 | MyGo 的 automation 插件 |
| 无法自动验证的 | 菜单栏、通知、开机自启、签名与公证,列为人工验收清单 |

`make check` 是合并前的唯一关卡,在 macOS 和 Linux 上都要通过。

### 13.4 教训机制

- 定期回顾已合并的改动:哪些返工了,哪些验证得太浅。
- 每条教训写成"规则、原因、证据",记入 LESSONS.md。
- 同一条教训在三个不同的日子出现,就移入代码规范成为正式规则,并尽可能配一条检查。
- AGENTS.md 要求改代码前先读 LESSONS.md。

### 13.5 必须由人决定的事

需求范围变化、新增第三方依赖、接口的不兼容改动、认证与令牌相关的任何改动、与已有决策记录冲突的做法。

## 14. 验收标准

每一行在实现时对应至少一个自动化测试;标注"人工"的由人验收。

| 测试项 | 通过标准 |
|---|---|
| 表单建任务 | 不写任何配置文件,在应用里建出脚本任务、AI 任务和多步骤任务 |
| 关闭窗口 | 关闭窗口后任务仍按时执行(人工) |
| 定时执行 | 按任务指定的时区触发 |
| 睡眠与重启 | 错过的触发按策略补跑一次或记为错过,不重复触发 |
| 日志 | 保存输出、退出码和当时的配置快照 |
| 超时 | 超时后终止整棵进程树 |
| 并发 | 同一任务上次未结束时,本次跳过并记录 |
| 多步骤 | 步骤按顺序执行并能引用前面步骤的输出;某步失败后续不执行;某步声明无事可做时后续不执行且不通知 |
| 中断恢复 | 后台异常退出后重启,运行中的记录标为中断 |
| AI 命令行 | 用假 agent 完成一次非交互执行并保存结果;agent 等待确认时明确失败 |
| 静默 | 结果信封或静默标记表示无内容时不发通知 |
| 产物 | 声明了产物文件而文件不存在时,运行记为失败 |
| 通知投递 | 投递失败后重试投递,不重跑任务;同一结果不重复通知 |
| 凭证 | 存档和通知中不出现环境变量文件里的明文值 |
| 认证 | 不带令牌的请求全部被拒绝;默认只监听本机 |
| 幂等 | 重复提交同一个创建或运行请求,只生效一次 |
| 远程 | 在应用里打开另一台主机;主机离线时显示离线而不是任务失败 |
| 系统通知与开机自启 | 通知能弹出并点击直达结果;重启电脑后应用静默驻留(人工) |
