# 0013 Webhook 的请求格式和重试

日期:2026-11-12

## 决定

任务的通知可以有 `webhook` 渠道:`{"channel": "webhook", "url": "https://…", "when": "on_content"}`。时机的含义与系统通知相同(N2)。

运行结束后,后台向这个地址发一个 POST,请求体是 JSON:

| 字段 | 含义 |
|---|---|
| `event` | 目前只有 `run.finished` |
| `task`、`run_id`、`status` | 任务名、运行编号、运行状态 |
| `no_content` | 是否无内容(T7、O4) |
| `title`、`body` | 与系统通知相同的标题和正文(N5) |
| `summary` | 结果摘要 |
| `artifacts` | 产物文件的完整路径,没有时是空数组 |
| `started_at`、`finished_at` | RFC 3339 时间 |

请求头带 `Content-Type: application/json`、`User-Agent: bugu`,以及 `Idempotency-Key: <运行编号>/<通知序号>`。

- 对方返回 2xx 算送达。
- 4xx(408 和 429 除外)说明请求本身不被接受,不再重试。
- 其他失败在 30 秒、2 分钟、10 分钟、1 小时之后各重试一次,一共尝试 5 次,之后记为失败。
- 每次请求最多等 10 秒。

每条通知在运行目录的 `deliveries/` 下有一条投递记录:渠道、目标、状态、尝试次数、最近一次的失败原因、下次重试时间、去重标识(N7)。后台重启后接着投递没有发完的 webhook。系统通知也留记录,但只在运行结束的那一刻发,不重试。

## 理由

- 请求体自己带上标题和正文:接收方转发到聊天工具时不必再拼一遍,内容也和系统通知一致。
- 去重标识在重试时不变:网络超时后对方其实可能已经收到,重发时接收方可以据此丢掉重复的那条。
- 重试间隔拉长到一小时:接收方短暂不可用的情况占多数;长时间不可用时,继续高频重试没有意义。
- 投递记录放在运行目录里:随运行一起保存和清理,查一次运行就能看到它的通知去了哪里。

## 后果

- 请求体和请求头是对接收方的约定,改字段含义要新写一篇决策记录。
- webhook 地址写在任务定义里。地址本身带密钥的(很多聊天工具的机器人地址就是这样),任务文件要和密钥一样对待。
- 国内聊天工具的机器人(N4)需要各自的请求格式,以后作为单独的渠道加入。
