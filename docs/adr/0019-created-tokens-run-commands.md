# 0019 另外创建的令牌等于能执行任意命令

日期:2026-11-14

## 背景

[0015](0015-tokens-and-hosts.md) 把令牌分成两级:本机令牌能访问全部接口;另外创建的令牌不能管理令牌,也不能读写登记的其他主机。理由是登记表里有其他主机的令牌,交给某个 agent 的令牌不该连带泄露它们。

但另外创建的令牌能新建、修改和立即运行任务,而任务就是以运行后台的用户身份执行任意命令。一个任务可以直接读数据目录里的 `token`、`hosts.json`,也可以读这个用户能读的任何文件。所以两级访问挡不住持有另外创建的令牌的人:他多建一个任务就能拿到本机令牌和其他主机的令牌。安全审查指出了这一点。

可选的做法:

1. 写明另外创建的令牌就是全权限,不改代码。
2. 另外创建的令牌只能查看和触发已有任务,不能新建、修改任务和运行器。边界是真的,但别的机器上的 agent 就不能通过 `--host` 建任务了,要改需求。
3. 把其他主机的令牌移到系统钥匙串,并让任务读不到数据目录。macOS 上可行,Linux 上没有统一的钥匙串,任务的沙箱也做不完整。

## 决定

采用第 1 种。

- 另外创建的令牌视为与本机令牌同等的信任:持有它的人能以运行后台的用户身份执行任意命令,能读到这个用户能读的一切,包括本机令牌和其他主机的令牌。
- 0015 的两级访问保留,但只当作防误操作的分隔,不当作安全边界:另外创建的令牌不能直接列出、新建、作废令牌,也不能直接读写登记的其他主机。
- `bugu token create` 在给出令牌时提示这一点;README 的远程管理一节写明只把令牌交给信任的机器。

## 理由

- 目前令牌只发给使用者自己的机器(另一台电脑、服务器上的 agent),给它们全权限符合实际用法。
- 第 2 种会去掉"在服务器上让 agent 建任务"这个用法(PRD 5.4、`--host`),现在没有需要它的场景。
- 第 3 种在 Linux 上做不完整,做了也只是挡住读登记表,挡不住执行任意命令本身。
- 把现状写清楚比留着一个看起来像边界的分隔更安全:使用者据此决定把令牌交给谁。

## 后果

- 令牌泄露等于这台主机上该用户的账户泄露。发现泄露时用本机执行 `bugu token revoke` 作废,立即生效。
- 以后要把令牌交给不完全信任的一方(别人的机器、公开的服务)时,需要另写决策记录,做第 2 种或更严格的限制。
