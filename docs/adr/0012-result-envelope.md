# 0012 结果信封的格式

日期:2026-11-12

## 决定

任务可以在 `{run_dir}/result.json` 写一个 JSON 对象,说明这次运行的结果(O12)。每个字段都可以不写,不认识的字段忽略:

| 字段 | 含义 |
|---|---|
| `status` | `succeeded`、`failed` 或 `no_content` |
| `summary` | 一句话的结果摘要,用于收件箱和通知 |
| `artifacts` | 产物文件的路径列表;相对路径相对于 `{run_dir}`。列出的文件必须存在,否则本次记为失败 |
| `notify` | 是否请求业务通知:`true` 时即使没有输出也通知,`false` 时不通知 |
| `message` | 通知正文,优先于摘要 |

规则:

- 有信封时以它为准,没有时退回到退出码和静默标记。
- 信封能把成功改为失败或无内容,不能把失败的步骤改为成功:步骤失败时运行已经停止,不再读信封。
- 每一步结束后都读一次信封。中间某一步写了 `"status": "no_content"`,后面的步骤不再执行(T7)。
- 信封不是合法的 JSON,或 `status` 不认识,本次记为失败,原因里写明。
- `notify` 只影响"有内容时"这个通知时机;"总是"和"仅失败"照旧。

## 理由

- 退出码只能表达成败,AI 命令行步骤的退出码由工具决定,任务自己控制不了。信封让 agent 和脚本都能用写文件的方式说清结果。
- 放在 `{run_dir}` 里:每次运行一个新目录,不会读到上一次留下的信封。
- 字段都可选、不认识的忽略:agent 写出的 JSON 常带多余字段,严格拒绝会让任务无故失败。
- 不允许把失败改成成功:否则一个写错的信封能掩盖真正的失败。

## 后果

- 信封格式是任务和 Bugu 之间的约定,改字段含义要新写一篇决策记录。
- 列在信封里的产物和任务设置的产物(`output`)都记在运行的 `artifacts` 里。
