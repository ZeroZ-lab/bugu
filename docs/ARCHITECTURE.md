# 架构

一个 Go 程序,多种运行形态,共用一个后台。设计意图和需求见 [PRD](PRD.md) 第 5 章,各项决定的理由见 [adr/](adr/)。本页只描述代码现状。

## 运行时

程序入口为 `main → cli`。`bugu serve` 在当前进程里启动后台(`daemon`);`bugu app`(或不带参数)启动桌面应用(`gui`),它同样在进程里承载后台,除非本机已有后台在运行,那时它只做界面。其余命令是客户端:通过 `client` 调用后台的 HTTP 接口,自己不读写任务文件。

```
bugu add / list / run / …          bugu serve
        │                               │
     client ──── HTTP JSON + 令牌 ──→ server ──→ daemon 的引擎
                                                   ├─ schedule  现在该触发什么
                                                   ├─ exec      预检、启动进程、超时、采集输出
                                                   │   └─ runner  运行器配置 → 要执行的命令
                                                   └─ store     任务文件、运行存档、调度进度
```

后台每 15 秒醒来一次,用当前墙上时间和每个任务"已评估到的时间点"计算该不该触发,不设长定时器([ADR 0003](adr/0003-injected-clock.md))。评估点在触发前落盘,所以重启不会重复触发。停机或睡眠跨过多个时间点时,按任务的补跑策略处理:默认只补最近一次,也可以不补或只在宽限时长内补,不补的留一条"错过"的记录。两次评估之间隔得比几个评估间隔还久就算睡过;刚醒来或刚启动时,补跑要等连续醒着两分钟之后才启动,按时的触发不等([ADR 0016](adr/0016-catch-up-after-wake.md))。cron 按任务的时区计算,没有设置时按主机时区;程序内嵌了时区数据。任务可以设随机偏移:每个时间点的实际触发时间是原定时间加上一个由任务名和时间点散列出的偏移,评估、补跑和"下次运行"都按实际时间,模板里的时间去掉偏移([ADR 0018](adr/0018-schedule-jitter.md))。同一任务上一次未结束时,新的定时触发记为跳过。

本机客户端靠数据目录(默认 `~/.bugu`,可用 `BUGU_HOME` 指定)里的两个文件找到后台:`endpoint.json` 是后台实际监听的地址,`token` 是令牌。数据目录由一个文件锁独占,同一份数据只会有一个后台。目录布局见 `internal/store/store.go` 的注释,接口列表见 `internal/server/server.go`。

每个接口请求先校验来源再校验令牌,之后才到达处理器:带 `Origin` 的请求必须与请求目标同源,令牌只从 `Authorization: Bearer` 请求头读取([ADR 0001](adr/0001-http-and-token.md),PRD 7.10)。

## 界面

前端源码在 `web/`,用 TypeScript 编写,Vite 构建,没有运行时的第三方依赖:页面由原生的自定义元素组成,`web/src/dom.ts` 是手写的渲染辅助([ADR 0017](adr/0017-web-components-no-framework.md))。构建产物 `index.html`、`app.js`、`style.css` 写进 `internal/server/static/` 并提交进仓库,编译时嵌入程序,由后台在同一端口提供,所以构建程序不需要 Node([ADR 0010](adr/0010-web-react-vite.md))。`web/src/api.ts` 是接口客户端,`taskForm.ts` 是表单与任务定义之间的转换,`mdparse.ts` 和 `Markdown.ts` 把结果按 Markdown 显示(只生成元素,不插入 HTML),`ui/` 是共用组件,其余是页面上的自定义元素。新建和修改任务是单独的页面,地址是 `#/new` 和 `#/edit/<任务名>`,与 `#token=` 这类参数片段区分开。`web/e2e/` 是浏览器测试:用构建好的程序起一个临时数据目录、随机端口的后台,在 Chromium 里走主要流程。前端只通过 JSON 接口工作,所以浏览器和应用窗口里是同一份。这三个静态文件不需要令牌;令牌由桌面外壳放在网址片段里交给页面,或由用户在页面上粘贴([ADR 0007](adr/0007-static-pages-without-token.md))。

桌面外壳 `gui` 是全项目唯一引用桌面框架 MyGo 的包,只做开窗口、菜单栏图标、系统通知、开机自启和退出前确认。用 `headless` 构建标签编译时不包含它和框架(`make build-headless`)。`make app` 把程序打成应用包,配置在 `mygo.json`。

运行结束后,`notify` 按任务的通知设置决定要不要通知、内容是什么。每条该发的通知先在运行目录里建一条投递记录,再投递:系统通知通过 `daemon.Options.Notify` 交给承载后台的外壳去显示,`bugu serve` 没有外壳,系统通知记为未发出;webhook 由 `deliver` 发送,失败按间隔重试,后台重启后接着发([ADR 0013](adr/0013-webhook-delivery.md))。投递失败只重试投递,不重跑任务。

## 命令行与远程

命令行的全局参数可以写在任何位置:`--json` 让标准输出是接口的 JSON,出错时标准错误是 `{"error": {"code", "message"}}`,代码沿用接口的错误代码,另有 `usage`、`unavailable`、`error`(A1);`--host <名字>` 改为连接登记过的另一台主机;`--lang` 见下一节。

访问令牌分两级([ADR 0015](adr/0015-tokens-and-hosts.md)):数据目录里 `token` 文件的本机令牌能访问全部接口;`bugu token create` 创建的令牌只存哈希,能管理任务,不能管理令牌和登记的主机。处理器按路径区分,`/tokens` 和 `/hosts` 只对本机令牌开放。登记的其他主机存在 `hosts.json`,命令行直接读写它,网页面板经本机后台读写;后台列出时逐个检查连接状态。在应用里打开另一台主机时,窗口载入那台主机自己的网页面板,本机不代理请求。

`bugu daemon install` 经 `service` 把 `bugu serve` 注册为 LaunchAgent 或 systemd 用户服务。`bugu web` 在没有桌面应用的机器上启动后台并打开网页面板;本机已有后台时只打开它的面板。

## 语言

界面说中文和英文([ADR 0014](adr/0014-interface-languages.md))。Go 代码里的文字用中文原文交给 `i18n`,英文译文在 `internal/i18n/en.json`;网页的在 `web/src/i18n.ts` 和 `web/src/locales/en.json`。网页的外观(浅色、深色)不经过后台,只记在浏览器里,见 `web/src/theme.ts`。后台按设置的语言(或系统的语言)写通知、日志和运行说明;接口的错误信息按请求头 `Accept-Language` 的语言写,命令行和网页都带上这个头。设置存在数据目录的 `settings.json`。桌面外壳在语言改变后重设菜单和窗口标题,只做界面时从后台读取设置。

尚未实现的部分见 [PRD](PRD.md) 第 10 章。

全部在 `internal/` 下,按职责平铺。

| `clock` | 时钟接口、真实时钟、测试用假时钟 | 无 |
| `task` | 数据模型:任务、触发、步骤、运行 | `i18n` |
| `schedule` | 给定任务和当前时间,决定现在该触发什么。纯函数,不执行、不落盘 | `clock` `task` `i18n` |
| `runner` | 读取运行器配置,把 AI 命令行步骤渲染成要执行的命令,展开模板变量。不启动进程 | `task` `i18n`,以及仓库根目录的 `runners`(预设) |
| `exec` | 预检、经登录 shell 启动进程、超时、终止进程树、采集输出、检查运行器能否使用;演练(只列出将执行的命令) | `clock` `task` `runner` `i18n` `api` |
| `store` | 任务文件、运行存档、调度进度、设置、令牌文件的持久化,数据目录的独占锁 | `clock` `task` `i18n` |
| `notify` | 决定一次运行要不要通知、通知写什么。纯函数,不负责显示 | `clock` `task` `i18n` |
| `api` | HTTP 接口的请求与响应类型,以及客户端和后台共同约定的文件名。只有类型和常量,以及接口错误按语言说明的方式 | `task` `i18n` |
| `server` | HTTP 处理器、来源校验、令牌认证。通过自己定义的 `Backend` 接口调用后台 | `api` 与上面全部 |
| `daemon` | 引擎(触发、运行管理、通知投递、令牌、登记的主机,实现 `server.Backend`),并把以上各部分组装成一个运行中的后台 | `server` `deliver` `hosts` 与上面全部 |
| `deliver` | webhook 的请求格式、发送和重试间隔。不读写文件,投递记录由后台保存 | `task` `notify` `i18n` |

| `gui` | 桌面外壳:窗口、菜单栏、系统通知、开机自启。唯一引用桌面框架的包 | `client` `api` `clock` `task` `daemon` `notify` `i18n` |

| `service` | 把后台注册为当前用户的系统服务(launchd、systemd);外部命令经注入的函数执行 | `i18n` |
| `cli` | 子命令。通过 `client` 工作;仅在启动后台时引用 `daemon`,仅在打开桌面应用时引用 `gui` | `client` `api` `task` `daemon` `gui` `i18n` `hosts` `service` |

仓库根目录的 `runners/` 不在 `internal/` 下:它存放自带的运行器预设,加一个把它们嵌入程序的 Go 文件。厂商和产品的名字只出现在这里的配置文件里。`skills/` 同样在根目录:教 AI agent 使用 bugu 的技能说明(中英文各一份),嵌入程序,由 `bugu skill` 打印。

## 运行器

运行器是一个 JSON 文件,描述怎样调用一个命令行工具:启动命令、提示词怎么传(参数、标准输入或文件)、各权限级别对应的参数、退出码之外的成功条件、检查能否启动的命令。字段的含义见 `internal/runner/runner.go`。自带的预设在 `runners/`,用户自己的放在数据目录的 `runners/` 下,同名时用户的优先。配置在每次使用时重新读取,修改后不需要重启后台。

AI 命令行步骤默认以只读级别运行,放开要在任务里显式写出,且不能超过运行器配置里的上限([ADR 0008](adr/0008-agent-permission-levels.md))。限制由那个命令行工具自己执行,Bugu 只传递参数。

## 扩展边界

当前代码没有插件运行时或插件加载接口。运行器配置与应用插件的区别、对 Magpie 设计的取舍,见 [ADR 0006](adr/0006-extension-boundaries.md)。

## 执行核心

`exec.Executor` 接收注入的时钟和任务,校验后按顺序执行各个步骤(脚本、AI 命令行、文本),返回运行结果和每一步的结果。某一步失败、超时或被取消即停止;脚本以约定的退出码声明无事可做时也停止,但运行算成功且无内容;最后一步的输出包含任务的静默标记时同样记为无内容。执行器不解释触发和通知;它往运行的存档目录里写每一步的输出和 AI 命令行步骤实际发出的提示词,目录布局见 `internal/store/store.go` 的注释。

上一步的输出经文件交给下一步:脚本从标准输入读到它,提示词和文本里的 `{prev}`、`{steps.<步骤名>.output}` 原样代入,脚本命令里的则代入为读取文件的命令替换,输出内容不会被 shell 解释([ADR 0011](adr/0011-step-data-and-nothing-to-do.md))。任务的总时长上限在步骤之间共享,每一步还可以有自己的上限。多步骤任务运行中,每一步开始前执行器把各步骤此刻的状态交给后台,后台写进运行元数据,运行详情里的步骤卡片据此更新。正在执行的那一步的输出只在内存里,后台经 `exec.Live` 读取,读的时候脱敏,接口返回运行的输出时用它补上这一步,只给每路的最后 64 KB(G6);这一步结束后输出照常写进存档。每个任务有一个跨次运行保留的状态目录,由后台在运行前建好,以 `{state_dir}` 交给任务;任务没有指定工作目录时,各步骤就在这个目录里运行。

步骤全部成功后,执行器读取任务可能写下的结果信封 `{run_dir}/result.json`,以它为准决定成败、摘要、产物和是否请求通知([ADR 0012](adr/0012-result-envelope.md));任务设置了产物时,再把最后一步的输出保存为产物文件,或检查任务自己写的那个文件存在。产物目录在第一步启动之前预检。

## 收件箱

运行结束时后台给它留一句摘要(信封里有就用信封的)。有结果要看的运行进入收件箱:失败、超时、中断,以及有内容的成功;读过的在运行元数据里记下时间。收件箱没有单独的存储,每次从运行记录里筛出来。`store` 在内存里为全部运行记录保留一份只有任务、状态、是否未读等几项的索引,启动时读一遍运行目录建立,之后随每次写入更新;收件箱的计数、按任务查询、任务列表里的上次运行都先查索引,只读取要返回的那几条的元数据。桌面外壳每隔几秒查一次收件箱,按未读、失败和运行中的情况更新菜单栏图标和旁边的条数,画法见 [DESIGN.md](DESIGN.md)。

每一步启动之前先预检:工作目录是否存在,AI 命令行步骤的运行器命令能否找到。不通过就不启动,本次记为失败并说明原因。

后台由 `bugu serve` 或桌面应用启动时,子进程经用户的登录 shell 启动(`$SHELL -l -c 'exec "$@"'`),所以 PATH 和登录态与终端里一致;任务自己的环境变量在 shell 启动之后再设置,不会被启动文件覆盖。任务可以指定环境变量文件存放密钥,每次运行时读取,与任务自己的环境变量合并(任务的优先);文件里的值在每一步的输出、摘要和错误里替换为"[已隐藏 名字]",然后才存档、传给下一步或发出通知。只支持 sh、bash、zsh、dash、ksh;其他 shell 下直接启动,子进程继承后台的环境。超时使用可停止的时钟定时器,测试通过假时钟和进程握手驱动。每路输出在内存里只保留开头和结尾,超出上限的中间部分用一行说明代替。

macOS 和 Linux 上每次执行使用独立进程组。超时、取消及父进程退出后均清理组内后代,再收集输出;主动脱离进程组的程序不在此清理保证内。这类程序若仍持有输出管道,采集在父进程回收后的一段宽限期结束,运行的状态、退出码和结束时间仍取父进程的真实结果。执行器不是进程隔离沙箱。
