# Dogfood 的候选任务

按用户的实际需要改写,不要原样照搬。每件都先 `--dry-run`,再试跑一次。

## 抓取后只推新内容(场景二)

用户真正关心的两三个网站或 RSS,每天两三次。三步:

1. 脚本步骤:抓取,对照 `{state_dir}/seen.txt` 去重,新条目写进 `{state_dir}/pending.txt` 并输出;没有新条目时以退出码 75 结束(这次不通知)。
2. AI 命令行步骤(codex,只读):把新条目整理成简报,只根据标题,不编造。
3. 脚本步骤:`cat && cat {state_dir}/pending.txt >> {state_dir}/seen.txt && rm {state_dir}/pending.txt`,最后一步成功才算看过。

要观察的:没有新内容时真的安静;睡眠后只补跑一次;刚醒时网络还没好会怎样。

## 取数存档(场景三)

一份用户每天确实会看的数据(某个仓库、某个接口、某个本地日志的统计),每天固定时间。

- 取数用一条命令或一个自定义运行器(`bugu runner add`),成功条件写在运行器的 `success` 里。
- 对比 `{state_dir}` 里上一次的数据,AI 命令行写成日报。
- `--output-dir <用户的文件夹> --output-name "report-{date}.md"`。

要观察的:文件每天都在;取数失败时不调用 AI,并且通知到了。

## 传统脚本,只在失败时通知(场景四)

比如每晚把某个目录同步到备份盘。`--notify on_failure`。先备份到一个副本目录,确认可靠后再换成真的。

要观察的:成功时完全安静;备份盘没插时的失败说明看得懂。

## 让 agent 自己建任务(场景五)

用户把 `bugu skill` 的输出装进他常用的 agent(按用户要求不用 Claude 时,换成那个 agent 的技能或说明文件位置),然后说一句"以后每天早上帮我看一下 <仓库> 的新 issue"。

要检查的:agent 用了 `--json`、先演练再试跑、AI 步骤保持只读、把任务名和下次运行时间告诉了用户。
