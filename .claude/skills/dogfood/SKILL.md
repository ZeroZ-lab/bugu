# Dogfood 布谷

Dogfood 是用户自己每天靠布谷干真活,用真实的时间(睡眠、重启、断网、几周的记录)去撞自动化测试撞不到的问题。你是陪跑:搭好、巡检、记录、分诊。修复走 AGENTS.md 的正常开发流程,不在 dogfood 里顺手改。

约定,每个分支都适用:

- **日志**在 `~/.bugu-dogfood/`:`notes.md` 是摩擦记录(按时间追加,用户原话),`checkins/<日期>.md` 是巡检报告。日志不进仓库:它是过程,文档只写现状。
- **被 dogfood 的是用户真实在用的布谷**:打包的应用(`make app`)和它的数据目录(默认 `~/.bugu`)。你只读;建任务、改任务、删记录都先得到用户同意。
- **AI 任务用 codex 运行器**,不用 claude(用户的要求)。
- 所有 `bugu` 命令加 `--json`,按错误里的 `code` 判断。

按参数进入一个分支;没有参数时问用户要哪一个。

## setup

1. 确认用户在跑的是当前代码:`bugu doctor --json` 没有 `fail`,并且后台版本等于 `git rev-parse --short HEAD`。版本不对时,让用户用 `make app VERSION=$(git rev-parse --short HEAD)` 重新打包、退出旧应用再打开新的。
2. 和用户挑 3–5 件**真事**:每件都是用户确实想要结果的,不是演示用的玩具任务;合起来覆盖下面四类。候选和写法见 [TASKS.md](TASKS.md)。
   - 抓取后只推新内容(场景二),
   - 取数存档(场景三),
   - 传统脚本、只在失败时通知(场景四),
   - 让用户在他常用的 agent 里装上 `bugu skill` 的输出,用一句话让 agent 自己建任务(场景五)。这一件由用户和那个 agent 完成,你只检查结果。
3. 除场景五外的任务由你建:`bugu add … --json`,再 `bugu run <任务> --dry-run --json` 给用户看将执行什么,用户同意后试跑一次,用 `bugu logs <运行编号> --json` 确认结果是用户想要的。
4. 在 `notes.md` 开头写下:开始日期、版本、每个任务的名字、它多久跑一次、用户期待它做到什么。

完成标准:每个任务都试跑成功过一次,`notes.md` 里有这份清单。

## checkin

每 1–3 天一次,或用户觉得"好像哪里不对"时。

1. 运行 `python3 -I .claude/skills/dogfood/checkin.py --since <上次巡检的时间>`(上次的时间在最新一份 `checkins/` 里;第一次不给 `--since`)。它只读,输出这段时间每个任务的运行情况和**异常**:失败、超时、中断、错过、跳过、重复触发(同一原定时间跑了两次)、失败但通知一条也没送达、下次运行时间已过、距上次定时运行远超平时的间隔。
2. 逐条看异常:`bugu logs <运行编号> --json` 看输出和投递记录,必要时对照系统日志(macOS 上 `pmset -g log` 能看到睡眠和唤醒)。每条给出**判定**:
   - 产品问题:布谷做错了,或做法让人意外;
   - 任务自己的问题:脚本、提示词、外部服务出了错,布谷如实记录了;
   - 符合预期:比如设置为不补跑的任务记为错过。
3. 问用户一句:上次巡检以来,用的时候有没有别扭的地方。把回答按原话追加进 `notes.md`。
4. 写 `checkins/<日期>.md`:时间窗、每个任务的运行次数和结果、每条异常和判定、用户说的摩擦。

完成标准:每条异常都有判定;判为产品问题的,写清楚它是在什么条件下发生的。

例(第一次 dogfood 发现,已按决策记录 0016 修复):电脑 08:00 在睡眠,08:10 唤醒时立即补跑,抓取一步因为网络还没恢复(DNS 解析失败)而失败。判定是产品问题:补跑发生在网络可用之前。条件是睡眠跨过原定时间,醒来时网络尚未就绪。

## note

`/dogfood note <一句话>`:把用户的原话连同时间追加进 `notes.md`;能从上下文看出是在哪个界面或命令里遇到的,一并记下。只记录,不分析、不修。

## review

每周一次,或用户要求时。

1. 读上次 review 以来的 `notes.md` 和全部 `checkins/`,把说的是同一件事的合并成一条。
2. 每条归一类,并给出下一步:
   - **能复现的产品问题**:先写一个失败的测试(red),测试名或注释引用 PRD 编号,再按正常流程修;复现不了真实条件(睡眠、断网)时,用假时钟或注入的错误模拟那个条件。
   - **体验问题**:提出具体改法(文案、默认值、界面),按 docs/DESIGN.md 的规矩。
   - **需求以外**:列出来交给用户;改需求范围要先问人(AGENTS.md)。
3. 同一类错误在不同的日子出现,按 LESSONS.md 的机制记一条教训。
4. 判断 dogfood 能不能结束:连续 7 天没有新的严重问题(漏跑、重复跑、失败没通知、丢数据),并且用户愿意把真事交给它。能结束时告诉用户,由用户决定是否在 PRD 第 11 章把里程碑标为完成。

完成标准:每一条都有类别和用户认可的下一步。
